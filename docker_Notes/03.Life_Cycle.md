# Container Life Cycle

## 1. What is a Container Life Cycle?
- The container life cycle is the sequence of states a container goes through from creation to removal.
- A container runs as long as its main process (PID 1) is alive.
- When the main process exits, the container stops.
- The container engine (Docker, Podman, containerd) manages these states.

## 2. Stages of a Container

### Created
- The container is defined but not started.
- Command: `docker create <image>`
- The writable layer is prepared, but no process is running.
- `docker run` combines create + start in one command.

### Running
- The main process is executing.
- Command: `docker start <container>` or `docker run <image>`
- The container has CPU, memory, network, and filesystem access.
- If the main process exits, the container moves to Exited state.

### Paused
- All processes in the container are frozen using the cgroup freezer.
- CPU is not used, but memory and state are preserved.
- The container is not terminated; it can be resumed.
- Commands: `docker pause <container>`, `docker unpause <container>`

### Stopped / Exited
- The main process has ended.
- Causes:
  - Application finished normally (exit code 0).
  - Application crashed or errored (non-zero exit code).
  - OOM kill (out of memory).
  - Manual stop: `docker stop` sends SIGTERM, waits grace period, then SIGKILL.
  - Manual kill: `docker kill` sends SIGKILL immediately.
  - Container designed for short tasks exits after completion.
- The container still exists on disk, but no process is running.
- You can restart it with `docker start`.
- Stopping is normal behavior. It means the app is no longer running.

### Removed
- The container is deleted completely.
- The writable filesystem layer, metadata, and history are gone.
- Command: `docker rm <container>`
- Use `-f` to force remove a running container (sends SIGKILL first).
- Use `-v` to also remove anonymous volumes.
- Remove all stopped containers: `docker container prune`

## 3. Main Process and Exit

- PID 1 inside the container is the main process.
- When PID 1 exits, the container stops.
- Signals:
  - `SIGTERM` (15): graceful shutdown request. App should clean up and exit.
  - `SIGKILL` (9): force kill. Cannot be caught or ignored.
- `docker stop` sends SIGTERM, then SIGKILL after 10 seconds (default).
- `docker kill` sends SIGKILL by default (can send other signals with `--signal`).
- Exit codes:
  - 0: success.
  - Non-zero: error, crash, or signal.
- OOM kill: kernel kills the process if it exceeds memory limit.

## 4. Commands for Each Stage

```bash
# Create only
docker create --name myapp nginx

# Start a created or stopped container
docker start myapp

# Run (create + start)
docker run -d --name myapp nginx

# Pause and unpause
docker pause myapp
docker unpause myapp

# Stop gracefully
docker stop myapp

# Kill immediately
docker kill myapp

# Restart
docker restart myapp

# Remove stopped container
docker rm myapp

# Force remove running container
docker rm -f myapp

# Remove all stopped containers
docker container prune
```

## 5. Data Persistence Note

- When a container is removed, its writable layer is deleted.
- Data inside the container is lost unless stored in a volume or bind mount.
- Use volumes for databases and persistent data.
- `docker rm -v` removes anonymous volumes too.

## 6. Interview Points

### Common Questions & Answers
**Q: What are the states of a Docker container?**  
A: Created, Running, Paused, Exited (Stopped), and Removed. Restarting is a temporary state.

**Q: What happens when you run `docker stop`?**  
A: Docker sends SIGTERM to PID 1, waits 10 seconds, then sends SIGKILL if it does not exit.

**Q: Difference between `docker stop` and `docker kill`?**  
A: `docker stop` is graceful (SIGTERM then SIGKILL). `docker kill` sends SIGKILL immediately by default.

**Q: What happens to data when a container is removed?**  
A: The writable layer is deleted. Data is lost unless stored in a volume or bind mount.

**Q: How do you automatically remove a container after it exits?**  
A: Use `docker run --rm`.

**Q: What is the role of PID 1 in a container?**  
A: It is the main process. When it exits, the container stops. It should handle signals correctly.

**Q: How do you check why a container stopped?**  
A: `docker logs <container>`, `docker inspect <container>` (look at State.ExitCode, State.OOMKilled), and `docker events`.

**Q: What is a restart policy?**  
A: It tells Docker when to restart a container: `no`, `on-failure`, `always`, `unless-stopped`. Set with `--restart`.

### Product-Based Company Scenarios
**Scenario: A container keeps restarting in production. How do you debug?**  
Check `docker logs`, `docker inspect` for exit code and OOMKilled, and the restart policy. Fix the app or increase memory limits.

**Scenario: You need to run a one-time batch job. How do you ensure cleanup?**  
Use `docker run --rm` so the container is removed automatically after it exits.

**Scenario: A container is using too much memory and gets OOM-killed. What do you do?**  
Set memory limits: `docker run --memory=512m`. Monitor with `docker stats`. Optimize the app or increase limits.

**Scenario: You need to update a running container. What is the safe approach?**  
Stop the old container gracefully, remove it, and start a new one from the updated image. Use orchestration for zero-downtime.

### Service-Based Company Scenarios
**Scenario: Client says their app container stops immediately after start. Why?**  
The main process likely exits. Check the Dockerfile CMD/ENTRYPOINT. The process must run in the foreground (PID 1). Check logs for errors.

**Scenario: Client wants to pause a container to save CPU without losing state. How?**  
Use `docker pause`. It freezes processes and frees CPU but keeps memory. Resume with `docker unpause`.

**Scenario: Client needs to keep database data even if the container is removed. What do you recommend?**  
Use a named volume or bind mount. Do not rely on the container writable layer.

**Scenario: Client wants to clean up all stopped containers regularly. How?**  
Schedule `docker container prune -f` or use `docker system prune`.

## 7. Quick Takeaway
- Container states: Created -> Running -> Paused -> Exited -> Removed.
- Container lives while PID 1 lives.
- `docker stop` = graceful (SIGTERM then SIGKILL). `docker kill` = force (SIGKILL).
- Removing a container deletes its writable layer. Use volumes for persistence.
- Use `--rm` for short-lived containers.
- Use restart policies carefully to avoid crash loops.
