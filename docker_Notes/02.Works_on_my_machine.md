# Works on My Machine Issue & Environment Parity

## 1. The Problem
- Code works on the developer’s machine but fails in QA or Prod.
- Root cause: the environment around the code is different.
- This is called the **“works on my machine”** problem.

## 2. What is an Environment?
An environment is everything around your code:
- OS and kernel
- Runtime and software versions
- Libraries and system packages
- Configurations and environment variables
- Secrets
- Hardware limits: CPU, RAM, disk
- Network, DNS, firewall
- Permissions and file paths
- Data and database state
- Timezone and locale

### Dev, QA, Staging, Prod
- **Dev**: developer local machine, fast feedback, debug tools, mock services.
- **QA/Test**: functional and regression testing, test data, close to Prod.
- **Staging**: Prod-like, final validation, performance and security checks.
- **Prod**: live users, strict security, scaling, monitoring, backups.

## 3. Common Causes of Mismatch
- Different OS: Ubuntu vs Alpine vs Windows.
- Different runtime versions: Node 18 vs Node 20, Python 3.9 vs 3.12.
- Missing system libraries: libc, openssl, image processing libs.
- Different environment variables or secrets.
- Different CPU architecture: x86_64 vs ARM64.
- Different Docker engine or host kernel.
- Using mutable tags like `latest`.
- Different external services or data.

## 4. Fix: Containerization + Environment Parity
- Package application code, dependencies, runtime, and minimal OS userland into an image.
- Containers share the host kernel, so the host must be compatible.
- An image is immutable and portable.
- Build once, then promote the same image through Dev -> QA -> Prod.
- Keep configuration outside the image using env vars, secrets, and volumes.
- Pin versions.
- Keep Docker engine versions compatible.
- Match architecture or build multi-architecture images.

## 5. Docker Workflow Example

### Dockerfile
```dockerfile
FROM node:20.11-alpine3.19
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

### Build, Tag, Run
```bash
docker build -t myapp:1.0.0 .
docker run -d --name app -p 3000:3000 --env-file .env myapp:1.0.0
docker push registry.example.com/myapp:1.0.0
```

### Dev with Docker Compose
```yaml
services:
  app:
    image: myapp:1.0.0
    env_file: .env
    ports:
      - "3000:3000"
  db:
    image: postgres:16.2
    environment:
      POSTGRES_PASSWORD: devpass
```

### Multi-Architecture Build
```bash
docker buildx build --platform linux/amd64,linux/arm64 -t myapp:1.0.0 --push .
```

## 6. Rules for Consistency
- Do not bake config or secrets into the image.
- Use `.dockerignore`.
- Use multi-stage builds.
- Tag with version or Git SHA, not `latest`.
- Use image digest in Prod.
- Run containers as non-root.
- Scan images.
- Keep Dev/QA/Prod configs separate, but use the same image.

## 7. Interview Points

**Q: How does Docker solve “works on my machine”?**  
A: It packages the app, dependencies, runtime, and minimal OS into an immutable image. The same image runs in any compatible environment.

**Q: Does Docker solve all environment issues?**  
A: No. Config, secrets, data, network, external services, and architecture still matter. Use env vars, secrets, IaC, and multi-arch builds.

**Q: What is environment parity?**  
A: Keeping Dev, QA, and Prod as similar as possible so code behaves the same.

**Q: Why avoid the `latest` tag?**  
A: It is mutable. Different pulls can get different images. Use version tags or digests.

**Q: How do you promote an image?**  
A: Build once in CI, push to a registry, then promote the same digest through environments with different config.

**Q: Can Linux containers run on Windows or macOS?**  
A: Docker runs a Linux VM because containers share the Linux kernel. Windows containers need a Windows host.

**Q: What about x86 vs ARM?**  
A: Images are architecture-specific. Use multi-arch images or build per architecture. Emulation works but is slower.

### Product-Based Scenarios
- CI builds an image once. QA and Prod pull the same digest. Config is injected through env vars and secrets.
- Prod issue: compare image digests, env vars, config maps, secrets, and node architecture.
- Microservices: each service has its own image. Compose or Kubernetes ensures the same runtime.

### Service-Based Scenarios
- Client app fails in Prod but works in QA: check image tag/digest, env vars, DB version, network, and permissions.
- Legacy Windows app: use Windows containers or a VM.
- Client wants fast onboarding: provide a Dockerfile and Compose file so the Dev environment matches QA.

## 8. Quick Takeaway
- “Works on my machine” = environment mismatch.
- Container = app + dependencies + runtime + minimal OS userland.
- Build once, run anywhere with a compatible kernel and architecture.
- Same image + external config = parity.
- Containers reduce drift, but they do not remove the need for config, secret, data, and infrastructure management.
